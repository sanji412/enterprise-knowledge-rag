# 企业知识库 RAG：面试讲解与高频追问

这份材料用于理解和复述项目，不建议逐字背诵。面试时只说自己能解释、能定位代码、能现场修改的内容。

## 1. 30 秒项目介绍

我基于 Doc-Ingestion 开源基线做了一个中文企业知识库可信问答系统，主要处理员工手册、产品说明书和售后 FAQ。入库阶段用中文结构切片，同时建立 Jieba BM25 和 BGE-large-zh 的 Qdrant 向量索引；查询阶段用加权 RRF 融合两路召回，可选 Cross-Encoder 重排，再让 DeepSeek 只依据证据生成答案。生成后还会解析和验证引用，证据不足就明确拒答。我做了 30 条分级用例和 4 组消融，共 120 次真实评测，Hybrid 的 Hit@5 和 MRR@5 都是 1.0，事实覆盖 0.92，拒答准确率 0.9333。

## 2. 2 分钟完整讲法

项目要解决的不是普通聊天，而是“企业文档里的答案怎样找得准、说得有依据、错了能发现”。

首先是文档入库。我对 PDF、DOCX 和 Markdown 做统一解析，增加 `zh_structure` 中文切片，优先按章节、段落和中文标点断开。每个切片保存文件名、页码、章节和内容哈希，并生成稳定 chunk ID。同一个 ID 同时写入 Jieba BM25 和 Qdrant，这样检索、引用和评测能追到同一段原文。

其次是问答链路。问题同时进入 BM25 和 BGE-large-zh 向量检索。BM25 擅长型号、故障码、金额和时间，向量检索擅长同义改写。我没有直接相加两边分数，而是用加权 RRF 按排名融合，因为两种分数的量纲不一致。融合后可用 BGE-reranker-v2-m3 重排，再在 token 预算内拼接证据，请 DeepSeek 只根据证据回答并带 chunk 引用。

最后是可信控制。系统先把模型引用映射回本次召回的切片，再校验引用是否能支持答案主张。召回置信度太低、没有引用或引用不支持时返回 `refused`，而不是让模型用常识补全。

我还建立了评测闭环：30 条用例按 Easy、Medium、Hard 各 10 条，其中 5 条必须拒答；对 BM25、Vector、Hybrid、Hybrid+Rerank 共跑 120 次真实 DeepSeek 请求。结果说明 Hybrid 综合最好，而重排在小语料上没有增益，P95 反而从 2.72 秒上升到 10.47 秒。这个结果让我明确了组件不能只堆，需要用消融做取舍。

## 4. 一条问题在系统里怎样流转

以“ATLAS-X2 出现 E03 且重启后仍异常，要长按复位键多久”为例：

1. FastAPI 校验请求和模型配置。
2. BM25 命中 `ATLAS-X2`、`E03`、`重启` 等词。
3. BGE 把问题编码成 1024 维向量，从 Qdrant 召回语义相关切片。
4. 加权 RRF 合并两组候选，稳定 chunk ID 去重。
5. 可选 Cross-Encoder 对问题与候选逐对打分。
6. Context Optimizer 选择前 5 个证据并控制在 4000 token 内。
7. DeepSeek 生成“长按 8 秒”，同时输出 `[Doc <chunk_id>]`。
8. Citation Tracker 解析 ID，Citation Verifier 检查它来自本次召回且能支持主张。
9. Grounding Policy 通过后返回 `answered`；React 展示答案、文件名、章节和原文。

询问“公司今年给每位员工发多少年度奖金”时，知识库没有该事实，系统最终返回标准拒答。

## 5. 高频追问与标准回答

### Q1：这和直接调用 DeepSeek API 有什么区别？

直接调用只给模型一个问题，答案依赖模型预训练记忆。本项目在调用前检索企业私有文档，把证据放进上下文；调用后还解析和验证引用，并有拒答策略。所以重点不是“接了 API”，而是证据检索、上下文组织、可追溯引用和质量评测形成闭环。

### Q2：为什么要同时用 BM25 和向量检索？

两者互补。BM25 对型号、错误码、专有名词、日期和金额这类精确词更可靠；向量检索能处理同义词和自然语言改写。消融中 Vector 的 MRR@5 是 0.96，Hybrid 恢复到 1.0，也说明精确召回补足了语义召回的排序问题。

### Q3：为什么不用两个分数直接加权相加？

BM25 分数和向量相似度量纲不同，而且会受语料规模与模型影响。RRF 只使用每一路的相对排名，公式是 `Σ weight/(k+rank)`，更容易稳定融合和解释。

### Q4：Embedding 和 Reranker 有什么区别？

Embedding 分别编码问题和文档，可以提前算好文档向量，适合从大量文档快速召回；Cross-Encoder 同时读取问题和一个候选，相关性判断通常更细，但每次查询都要逐对推理，速度慢。所以一般先召回较小候选集，再重排。

### Q5：为什么选择 BGE-large-zh？

项目是中文企业问答，需要中文语义检索；BGE-large-zh-v1.5 输出 1024 维向量，生态成熟，也能在 sentence-transformers 中本地运行。选择不是只看模型名，代码还把 embedding profile 写入 collection 名并校验维度，避免换模型后误用旧索引。

### Q6：为什么要稳定 chunk ID？

如果每次入库都随机生成 ID，重复入库会产生重复向量，黄金证据和答案引用也会失效。稳定 ID 让 BM25、Qdrant、召回、引用、评测共享一个身份，支持幂等入库和端到端追溯。

### Q7：中文切片为什么不能只按固定长度？

固定长度可能把标题和正文、条件和结论切开。`zh_structure` 优先章节、段落和中文句末标点，超长时再按长度兜底，并保留重叠。这样证据更完整，引用展示也更自然。

### Q8：怎样判断该拒答？

有两道门。生成前，如果没有候选达到最低召回置信度就直接拒答；生成后，如果没有引用、引用解析失败、引用不是 `supported`，或校验分数低于阈值，也拒答。拒答用结构化 `status=refused` 返回，不当作 500 异常。

### Q9：引用验证是不是让另一个大模型判断？

本次正式报告没有使用未实测的 NLI 大模型分数。主要依靠引用结构解析、切片映射、文本/语义支持规则和黄金 evidence anchor 评测。这样成本低、可复现，但复杂语义支持仍有局限，后续可以引入经过单独评测的 NLI 或 LLM Judge。

### Q10：为什么 Rerank 结果反而差？

这次语料只有 27 个切片，Hybrid 已把黄金证据排到前 5，重排空间很小；Cross-Encoder 还显著增加推理时间，并可能改变送给 DeepSeek 的证据组合。实测 P95 从 2.72 秒变成 10.47 秒，事实覆盖从 0.92 降到 0.88。所以我不会说重排必然提升，而会在更大语料、模型常驻后重新评估。

### Q11：Hit@5 和 MRR@5 有什么区别？

Hit@5 只看前 5 是否出现黄金证据；MRR@5 还看第一次命中的位置，第一名是 1，第二名是 0.5。两个指标结合能区分“勉强召回”和“证据排在最前面”。

### Q12：为什么正确拒答不计入 Hit@5 和引用解析率的分母？

应拒答问题没有黄金答案证据，要求它命中会人为压低检索指标；正确拒答也不会产生答案引用，把它当成 0 引用会错误压低引用指标。因此检索/事实指标只统计可回答用例，引用指标只统计实际回答，拒答准确率则统计全部 30 条。

### Q13：如何保证评测没有只挑成功结果？

运行器固定读取 30 条数据，对四组配置逐条执行，共 120 条；异常被写成失败记录，不会省略。JSON 保存生成时间、模型、配置、逐条结果、原始执行 commit 和聚合 commit；执行成功率必须是 1.0。

### Q14：Docker 里为什么要 Redis？

Redis 在这里主要保存分布式限流状态。即使 API 多进程或多实例，也能共享限流计数；Redis 不可用时有内存回退。不过生产环境还需要更严格的认证、监控和高可用，不应把演示 Compose 直接当生产架构。

### Q15：DeepSeek Key 怎么保护？

Key 从环境变量或请求头传给后端，只存在于当前进程/请求；不写进配置、索引、响应和日志。`docker/.env` 被 Git 忽略，仓库只提供 `.env.example`。冒烟测试还会断言响应中不包含 Key。

### Q16：如何处理文档更新？

当前稳定 ID 使相同内容重复入库幂等，但还没有完整的版本管理。生产化需要为文档增加版本、更新时间和有效期；更新时删除旧版本切片、增量写入新版本，并检测历史引用是否过期。

### Q17：如果 Qdrant 挂了怎么办？

健康检查会显示依赖异常，向量写入或查询失败时不应假装成功。可以降级到 BM25，但必须在响应中明确当前检索模式；本项目当前正式链路倾向失败可见，而不是静默返回不完整结果。

### Q18：项目最有价值的工程点是什么？

不是某一个模型，而是统一的证据身份和评测闭环：稳定 chunk ID 贯穿双索引、召回、引用和黄金用例；30 条分级数据和四组消融能用同一口径判断改动到底改善了什么、牺牲了什么。

## 6. 面试官要求现场修改时

可以优先做这些边界清晰的修改：

- 调整 `grounding.min_retrieval_confidence`，解释拒答率与召回容错的权衡。
- 改 RRF 两路权重，并运行检索单测或小评测。
- 新增一个企业 FAQ 和对应黄金用例，重新入库验证稳定 ID。
- 在前端证据卡片增加一个已有元数据字段。
- 给 `GroundingPolicy` 增加一个失败测试，再实现规则。

不要在不理解时直接改全链路。先从请求/响应、日志、逐步延迟和检索轨迹定位问题，再只改变一个变量。

## 7. 必须真正理解的知识清单

- RAG 的目的、局限，以及它为什么不能保证绝对正确。
- BM25 的词频、逆文档频率和长度归一化直觉。
- Embedding、余弦相似度、向量维度和归一化。
- RRF 公式和为什么适合异构检索融合。
- Bi-Encoder 与 Cross-Encoder 的准确率/延迟权衡。
- chunk size、overlap、结构切片对召回的影响。
- Prompt 中证据边界、引用格式与提示注入风险。
- Hit@K、MRR、事实覆盖、引用准确、拒答准确的口径。
- FastAPI 请求模型、SSE 流式响应、Docker Compose 和服务健康检查。
- API Key、日志脱敏、会话隔离和生产 RBAC 的区别。

## 8. 诚实回答不会的问题

推荐结构：

> 这个点我目前没有在项目里实际实现，所以不会把它说成已完成。我现在的理解是……如果要加入现有系统，我会先……然后用……指标验证。

例如被问到知识图谱：

> 这个项目当前没有做知识图谱，主链路是混合检索 RAG。我理解知识图谱更适合实体关系明确、多跳关系查询的场景。如果要加，我会先从现有文档抽取实体关系，同时保留原文 chunk 作为证据，最后用多跳问题和引用正确率验证，而不是直接替换当前检索。

这种回答比硬背一个没有做过的模块更可信。
